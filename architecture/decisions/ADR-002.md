# ADR-002 - PostgreSQL Schema per Module

| Status | Created Date | Decision Date | Updated Date |
|--------|--------------|---------------|--------------|
| Accepted | 10 Aug 2026 | Jun 2026 | 10 Aug 2026 |

## Context

- StockFlow is designed as a modular monolith with clearly defined module boundaries
- The architecture should allow modules to be extracted into independent services in the future with minimal database redesign
- StockFlow is a multi-tenant platform where data isolation between organisations is required
- The database design should balance maintainability, scalability, and operational cost

## Options Considered

| Option | Description |
|--------|-------------|
| `Shared Database, Shared Schema` | All modules share the same schema and tables |
| `Shared Database, Separate Schema by module` | Single database that each module owns its own schema and tables |
| `Database per Tenant` | Each tenant has its own dedicated database |


## Decision

- Adopt a `Shared Database, Separate Schema by module`

## Reason

- Clear database ownership by each module
- Easier migration of a module into an independent service in the future
- Lower infrastructure and operational cost

## Consequences

### Positive

- Clear database ownership for each module
- Simplify future migration to microservices
- Easier maintenance
- Lower infrastructure cost

### Negative

- Teams must enforce module boundaries through application design
- A database failure affects every module
- More complex of database permission and migration
- Cross schema queries may happen if team members do not understand the architecture and module boundaries
