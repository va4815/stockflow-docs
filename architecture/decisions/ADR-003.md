# ADR-003 - UUID or BIGINT

| Status | Created Date | Decision Date | Updated Date |
|--------|--------------|---------------|--------------|
| Proposed | 12 Aug 2026 |  | 12 Aug 2026 |
| Accepted |  | 13 Aug 2026 | 13 Aug 2026 |

## Context

- Decide the primary key strategy for tables in PostgreSQL
- The identifier strategy should balance simplicity, performance, storage cost, and future scalability

## Options Considered

| Option | Description |
|--------|-------------|
| `BIGINT` | All tables use `BIGINT` as primary key |
| `UUID` | All tables use `UUID` as primary key |
| `Hybrid` | Use `UUID` for externally exposed entities, `BIGINT` for internal tables |


## Comparison

| Option | Pros | Cons |
|--------|------|------|
| `BIGINT` | Smaller size (8 bytes) | Sequential and predictable |
|  | Smaller indexes | Requires coordination when IDs are generated across multiple independent writers |
|  | Efficient for joins and lookups | Less suitable for distributed ID generation |
|  | Easy to read and debug | |
| `UUID` | Globally unique | Larger size (16 bytes) |
|  | Can be generated independently without a central sequence | Larger indexes |
|  | Harder to predict or enumerate | Harder to read and debug |
|  | Better suited to multi-primary or distributed write architectures | Random UUID versions may have poorer index locality |
| `Hybrid` | Keeps UUID benefits for externally exposed entities | Introduces two identifier strategies |
|  | Uses `BIGINT` for simpler internal records | Requires clear rules for deciding which ID type to use |
|  | Reduces unnecessary UUID usage | Adds some implementation and maintenance complexity |


## Decision

Adopt `BIGINT` as the default primary key strategy for the initial stage of StockFlow.

## Reason

- StockFlow is expected to operate at a relatively small scale
- The initial database architecture uses a single region and a single write primary
- `BIGINT` provides sufficient identifier capacity for the expected workload
- `BIGINT` requires less storage and produces smaller indexes
- `BIGINT` is easier to read, debug, and operates
- UUID benefits such as distributed ID generation are not currently required
- The identifier strategy can be revisited if StockFlow later adopts a multi-primary or distributed write architecture
